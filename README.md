# Aran

Reviews content **before it is published**, checks it against an organisation's *own* approved guidelines and facts,
**explains every flag with the exact source it relies on**, suggests fixes that keep the writer's intent, and runs
decisions through a role-based approval workflow. People decide; the system never approves or publishes.

Pure Python standard library. No dependencies, no build step, no network needed.

## Run it (30 seconds)

```bash
python3 -m brandguardian          # then open http://127.0.0.1:8000
```

Python 3.12 is what it was run and tested on. The code was grammar-checked for 3.10 syntax but not run there.

## The two-minute path

1. Sign in as **Asha Rao (Creator)**. The guide strip at the top tells you what to do next.
2. Press **Load sample post**. Twelve notes appear, each with a *verified source* quote, a rule ID and a fix.
3. Accept the suggested fixes (the first button on each note). Blocking issues must be fixed before approval.
4. **Submit for review.** The draft locks.
5. Sign out, sign in as **Meera Iyer (Reviewer)**, open the item in **Review queue**, press **Approve**.
6. Press **Verify receipt**: four independent integrity checks pass.
7. Try the **Hallucination Trap** (tick the box under the editor) to watch the verifier reject fabricated model output.

Try also: sign in as Dev (agency user, sees only their own work), as Ravi (Insights, Guideline Health), and the **Trust** tab (Privacy X-ray and audit trail).

## How it works

```
 draft ──► exact detectors (no AI) ─────────────────────────┐
           terms · restricted phrases · claims vs Claim     │
           Ledger · voice · personal data · alt text · …    ├─► flags, each with: rule ID, verbatim quote
                                                            │   from YOUR guidelines/ledger, source, severity,
 draft ──► redact personal data ──► retrieve relevant rules │   suggestions (applied only if a person accepts)
           ──► AI judge (optional) ──► VERIFIER ────────────┘
                                        quote must exist verbatim · span must exist in the draft ·
                                        rule must exist · severity can only go down · rewrites may not
                                        add numbers or names. Anything else is rejected and counted.

 people ──► roles · versions · comments · diff · approve / approve with conditions / request changes
            approval re-checks the exact version on the server; blockers need a fix or a written override
            ──► hash-chained audit log ──► HMAC-signed approval receipt (verifiable)
```

Key ideas:

* **Evidence-or-Abstain.** No verified source, no flag. The model never judges its own citations; code does.
* **Claim Ledger.** Approved facts have an owner, a source and a valid-until date. A claim is *supported*, *contradicted*, *expired* or *unsupported (no approved source)*. "Unsupported" is deliberately not "false".
* **Streaming.** Results arrive per detector as they finish; stale reviews are cancelled when the user keeps typing.
* **Guideline Health.** If people keep dismissing or overriding the same rule, the rule is marked possibly unclear.

## Security model

* Bearer tokens, stored only as SHA-256 hashes; independent sessions; role checks enforced on the server; nobody approves their own content.
* Approval is checked against a fresh server-side review of the exact version; a forged client-side review cannot get blockers through.
* Strict Content-Security-Policy (`default-src 'self'`, no inline script or style), `nosniff`, `frame-ancestors 'none'`, no-referrer.
  The UI builds all DOM with `textContent`; user text is never parsed as HTML.
* Request body size and content-type limits, per-client rate limiting, a fixed allow-list of static files (no path joining from user input), errors without stack traces.
* Personal data and credentials are masked locally before any model call; the exact outbound payload is logged and shown (Privacy X-ray).
* Document text is treated as data: delimiter neutralisation in prompts, schema-validated model output, verifier gate, and visible detection of "instructions" hidden in copy.
* Knowledge-file regexes are validated (length limit and a heuristic guard against catastrophic backtracking).

## Honest limitations

* **The live Claude API call was not exercised.** It could not be reached from the build environment. Request building, response parsing and error handling are tested through an injectable transport and a local fake server; the verifier tests use scripted and simulated models. Verify with a real key before relying on the AI judge. The model name is configurable (`BG_MODEL`).
* The AI judge only adds *judgement* findings; all the exact checks work without it. Tone and messaging checks beyond measurable voice rules need the model.
* Receipts use HMAC, so verification trusts this server. Public-key signatures are planned.
* One process with SQLite: fine for a prototype, not multi-tenant, no horizontal scaling.
* Detectors know one brand's rules from a validated JSON file; there is no UI to edit guidelines yet.
* Rankings, claims and terms are matched with patterns, so unusual phrasing can be missed. The coverage panel shows which checks ran; it cannot show what a pattern missed.
* Fixes are span-level. Accepting several in one sentence can leave an awkward phrase (for example a dangling "designed to.") that a person should polish; the safe one-click default for an unsupported claim is removal, never a guessed rewrite.
* `Dockerfile` was written without Docker available and has not been built.
* Demo mode (default) enables account switching and the model simulator. Set `BG_DEMO=0` for anything real and create users with `python3 -m brandguardian add-user`.
